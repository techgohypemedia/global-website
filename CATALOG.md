# Product registry

The existing website remains at `/`. Open `/admin` for product management. QR codes open public pages at `/p/<permanent-id>`.

## Local setup

1. Use Node.js 22 or later and run `npm install`.
2. Run `npm run catalog:setup`. This creates a random `ADMIN_SETUP_TOKEN` in the ignored `.env.local` file without overwriting existing settings.
3. Run `npm run dev` and visit `http://localhost:3000/admin`.
4. Copy the token from `.env.local` into the initial setup form, then choose an email and a password of at least 12 characters. Subsequent visits use the email and password only.
5. Create categories, then add products or import CSV files using the downloadable templates.

The initial database is empty. There are no default credentials or demonstration records. One administrator account is supported. Passwords use salted scrypt hashes; sessions expire after eight hours. Admin mutations require an authenticated session and a matching request origin. Login attempts are limited to ten per fifteen-minute window.

## Business rules

- One record represents a product model with a unique SKU, not an individually manufactured unit. SKU comparison trims surrounding whitespace and ignores case.
- Serial numbers come from SQLite's transactional AUTOINCREMENT primary key, formatted as `PRD-000001`. They are immutable and are never reused. Sequence gaps are allowed.
- QR codes contain a permanent random product identifier. Product edits and SKU changes preserve the identifier and serial.
- Deactivation preserves the product, reserves its SKU, and changes the public page to “Product unavailable.” Reactivation restores it.
- Categories use trimmed, case-insensitive names. Categories assigned to products cannot be deleted, including when all assigned products are inactive.
- Product website URLs are required and must use HTTP or HTTPS. The full main-website product catalog is not generated by this feature.

## CSV

Product headers: `Product Name,SKU,Category,Brand,Model,Description,Manufacturing Date,Website URL`.
Required columns are `Product Name`, `SKU`, `Category`, and `Website URL`. Categories must already exist. Dates use `YYYY-MM-DD`.

Category header: `Category Name`.

Uploads support up to 5,000 rows / 2 MB. Each import is bounded and processed in one database transaction. Preview performs no writes. Commit validates again, skips duplicates in the database and file, imports valid rows, and retains a downloadable row report. Retrying a completed file does not duplicate products. This version does not have background jobs, resumable batches, or bulk updates; split larger files before upload.

CSV exports include inactive products, serials, QR URLs, and image URLs. Formula-like values are escaped for spreadsheet safety. Product images are uploaded through the form, not fetched from CSV URLs. Reimporting an export skips existing SKUs and does not update images or other existing fields. Row numbers count logical CSV records starting at 2 (blank lines are ignored; multiline records count as one record).

## Images and labels

Upload up to eight PNG, JPEG, or WebP images, each at most 5 MB. QR images can be downloaded as PNG or SVG. Product detail views include a print stylesheet for a 65 mm wide label. Use the browser's print scaling and paper settings appropriate to your printer.

## Deployment

The product registry supports Neon PostgreSQL (or other PostgreSQL databases) via `@neondatabase/serverless` when `DATABASE_URL` is set in `.env.local`:
```env
DATABASE_URL=postgresql://neondb_owner:...@...neon.tech/neondb?sslmode=require
```
When `DATABASE_URL` is provided, all categories, products, sessions, admins, and imports persist in Neon PostgreSQL. If `DATABASE_URL` is not provided, the registry falls back to local SQLite in `data/catalog.sqlite`.

Uploaded images live in `data/images` by default; set `CATALOG_DATA_DIR` to an absolute persistent directory to override it.

Set `APP_URL=https://your-final-domain.example` before generating production labels. It controls QR links, origin validation, and secure cookies. Preserve this domain for printed labels. Behind a reverse proxy, configure its public origin to match `APP_URL`. Serve production traffic over HTTPS.

Run `npm run build`, then `npm start`. Keep `.env.local` and the data directory private. Remove the setup token from production environment variables after the first admin has been created. Password recovery and additional admin roles are not included in this version.

## Verification

- `npm run test:catalog`: isolated database tests for imports, identity rules, updates, serial allocation, and exports.
- `npx tsc --noEmit`: TypeScript verification.
- `npm run lint`: repository lint. The existing website currently has unrelated lint errors in `app/about/page.tsx`, `AramcoHeader.tsx`, and `HeroSection.tsx`; the catalog files pass targeted lint.
- `npm run build`: production build.

The database tests use a temporary directory and do not touch the real catalog.

Browser verification is also available in `scripts/check-catalog-browser.mjs`. It uses installed Microsoft Edge (set `BROWSER_CHANNEL=chrome` for Chrome), creates test records, decodes the generated QR, and saves screenshots under `test-results/`. Run it only against an isolated local server. For example, in a separate PowerShell terminal:

```powershell
$env:CATALOG_DATA_DIR = Join-Path (Get-Location) '.catalog-test-browser'
$env:NEXT_BUILD_DIR = '.next-catalog-test'
$env:ADMIN_SETUP_TOKEN = 'catalog-browser-test-setup-token'
$env:APP_URL = 'http://127.0.0.1:3001'
npm run dev -- --hostname 127.0.0.1 --port 3001
```

Then run `node scripts/check-catalog-browser.mjs` from another terminal. Stop the isolated server afterward. These test environment settings must not be used for the real registry.
